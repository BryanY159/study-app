## 1. Decisions for you (defaults used if you approve as-is)

- **D1. Modules outside every group** (allowed, since groups are optional per module).
  The tree lists them at the top level, after the groups, in pack order, with no wrapper node.
  *Alternative:* put them under an "Other modules" node.
- **D2. Module order inside a group:** the pack's `modules` order, not the order of `moduleIds`.
  This keeps one order on every screen. Group order is the `groups` array order.
- **D3. `minModuleShare` when sections are set.** Sections decide the mix, so the per-module
  floor is **not applied** to a mock with sections, and `checkPack` warns if `minModuleShare > 0`
  alongside sections ("ignored when sections are set"). *Alternative:* apply the floor inside
  each section, which can conflict with small section counts and cause constant warnings.
- **D4. Section IDs must resolve.** A section naming an unknown group or module is an **error**,
  like groups. A content repo that keeps "pending" modules must leave them out of the sections
  it exports (noted for the content repo in M8).
- **D5. Section overlap.** Each module may be in **at most one section**, counting modules
  reached through a group. A section must name `groupIds` **or** `moduleIds`, not both, and
  not an empty list. `count` must be a positive integer. A module that is in no section is
  allowed, but `checkPack` warns that mocks never include it.
- **D6. Dashboard tree.** "Weakest topics" stays a flat ranked list (top 5, "Show all topics"),
  and each row shows its path (`First season › Glowroots`). The **"By module"** card becomes the
  group → module → topic tree, with accuracy and "answered / available" at every level.
  No checkboxes on the dashboard. *Alternative:* turn the weakest list itself into the tree.
- **D7. Expanded state.** Stored per device in `localStorage`, one key per screen and pack
  (`study-ui:tree:<screen>:<packId>`). It is **not** synced or backed up. It uses its own
  `study-ui:` prefix because `studyapp:` keys are treated as pre-v1.5 data by `legacy.ts`.
  If storage is blocked, the tree still works and just forgets.
- **D8. A preset selection** (`#/drill?topics=…`, "Drill weakest", related cards) also opens
  the branches that hold the preset topics, so she can see what was picked. This opening is not
  saved.
- **D9. N-5 wording.** I couldn't find N-5 in the files I was allowed to read (`app-backlog.md`
  only has A-1). **Please give me the new banner text** (today: "A new version of the app is
  ready. Reload to use it; your answers are saved."). Default if none is given: M7 is skipped
  and noted in §10.
- **D10. Not in this release:** per-section scores on the mock results screen; a section-aware
  drill. Both are easy to add later.

- Run: `npx vitest run src/pack src/engine`. No UI yet, so no e2e is related; the full e2e

## M2. Mock exam sections

**Code**
- `ExamBlueprintSchema.sections` **optional**: `[{ name, groupIds? , moduleIds?, count }]`.
- `checkPack` errors: counts don't add up to `questionCount` (shows both numbers); unknown
  group or module ID; neither or both of `groupIds`/`moduleIds`; a module in two sections (D5).
  Warnings: modules in no section (D5); `minModuleShare > 0` with sections (D3).
- `src/engine/mock.ts`, `assembleMock`:
  - no `sections` → today's code path, unchanged (the existing tests guard this);
  - with sections: each section gets its own pool (its modules' eligible questions, same
    exclusions as today: unconfirmed and `excludeIds`), split into scenario units with `toUnits`
    and shuffled. Units are taken while they fit the section's count, so **scenario sets are never split**
    and no section goes over its count;
  - if a section ends short (too few questions, or only scenario sets bigger than the gap),
    it warns in the same style as today: `Only 7 First season questions available (the exam
    blueprint asks for 10).` The mock then has fewer questions. Nothing is borrowed from other sections;
  - the final order is shuffled across sections, as today (units stay together).
- `Mock.tsx` already shows `warnings`; nothing new is needed there beyond the text.
- **Fixture:** Orrin's blueprint (6 questions) gets sections
  `First season` (`groupIds: [first-season]`, 3) and `Ember moss` (`moduleIds: [gamma]`, 3).
  Gamma's 3 eligible questions are one scenario set, so every mock includes it whole. Its
  unconfirmed question stays out, as today.

**Tests**
- `checks.test.ts`: every error and warning above; a pack with sections that add up passes.
- `mock.test.ts` (with `makePack`, extended to take `groups` and `sections`):
  - each section gets exactly its count over 200 seeds;
  - scenario sets are never split and never push a section over its count;
  - a short section → the warning and a smaller mock; other sections aren't affected;
  - a section reached by `groupIds` and one by `moduleIds` both work;
  - without sections, the same seed gives the **same mock as v2.0.0** (a snapshot of IDs taken before the change);
  - excluded and unconfirmed questions are never drawn.
- e2e `drill.spec.ts`/`app.spec.ts` mock flow: the Orrin mock has 6 questions, all 3 gamma
  scenario questions together, and no warning. A copy of the fixture with a section count raised
  past what's available shows the warning on the mock screen.

## M3. Topic tree: model and component

**Code**
- `src/ui/topicTree.ts` (pure, not part of the public contract):
  - `buildTree(ix, { includeTopic? })` → group → module → topic nodes (D1, D2). No `groups`
    → module → topic, exactly today's levels. Empty branches are dropped, e.g. modules with
    no cards on card setup;
  - `checkState(node, selected)` → `checked | unchecked | mixed`;
  - `toggle(node, selected, on)` → new selection (cascades down; parents follow from
    their children);
  - `sumCounts(node, perTopic)` → a count at every level (a generic callback, so drill, cards
    and the dashboard each pass their own numbers);
  - `topicPath(ix, topicId)` → `["First season", "Glowroots"]`.
- `src/ui/useExpanded.ts`: expanded IDs per screen and pack in `localStorage` (D7), all reads
  and writes in try/catch. Default: everything collapsed.
- `src/ui/components/TopicTree.tsx`, one component for all three screens:
  - each branch is a **disclosure button** (`aria-expanded`, `aria-controls`, chevron), plus
    an optional native checkbox with `indeterminate` for the mixed state. I'm using the disclosure
    pattern instead of an ARIA `tree` role on purpose: native buttons and checkboxes get Tab,
    Space and Enter behaviour and screen-reader support for free. A full `tree` role would need
    hand-written arrow-key handling, which is easy to get wrong.
  - keyboard: Tab moves through rows; Enter/Space on the chevron opens and closes; Space on a
    checkbox toggles it. Focus stays put when a branch opens, and a visible focus ring is shown;
  - every row and the chevron are **at least 44 × 44 px**. Indentation stays small on phones
    (about 12 px per level), names wrap instead of overflowing, and counts stay right-aligned;
  - a slot for each row's right side (counts, or the bar on the dashboard), and an "Expand all /
    Collapse all" link at the top. It's cheap and helps on desktop.
- Styles in `styles.css` use tokens only (light and dark).

**Tests** (`src/ui/topicTree.test.ts`, `TopicTree.test.tsx`)
- Model: grouped, ungrouped and mixed packs (D1); cascading and mixed state at all three levels;
  counts add up at every level; paths; empty branches dropped.
- Component: collapsed by default; expanded state survives an unmount and remount (same storage),
  is separate per screen and pack, and survives blocked storage; `aria-expanded` and
  `indeterminate` are correct; keyboard-only open, toggle and close with user-event.
- Run: `npx vitest run src/ui/topicTree src/ui/components/TopicTree`.

## M6. A-1: `flagged-fixed` for cards

**Code**
- `FlashcardSchema.status` adds `flagged-fixed`; `fixedIn` (positive integer) is allowed only on
  `flagged-fixed`, with the same refinement as questions.
- `flags.ts` `flagState`: card flags resolve like question flags. A flag made before `fixedIn`
  → "Resolved — re-check"; made on or after it → still "Open". A missing `fixedIn` counts as the
  current version, as for questions. The pre-flag rule stays.
- A `flagged-fixed` card is studied like a verified one (no chip, in every deck). Check
  `CardFace`, `CardSetup` and `leitner` for any `verified`-only test.
- **Fixture:** one Orrin card becomes `flagged-fixed` with `fixedIn: 1`.

**Tests**
- `cards.test.ts`: the new status parses; `fixedIn` on another status is rejected.
- `flags.test.ts`: the three card cases (before, on/after, no `fixedIn`), next to the question ones.
- `cardFlags.test.tsx`: the Flags screen shows "Resolved — re-check" for a fixed card in a v2 copy of the fixture.
- e2e: `cards.spec.ts` (the fixed card shows in a review like any other).
